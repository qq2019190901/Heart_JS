# 2026-09-27（续）— 联机功能审查，发现并修复一个致命 bug

## 结论：客户端收不到房主的任何广播（已修复）
`src/network/lan-peer.ts` 的 `setupHostChannel()` 定义了客户端侧的
`conn.on('data') → handleHostMessage` 注册逻辑，但**全项目无任何调用点**。
结果：房主 broadcast 的 `game-state` / `player-list` 客户端一律收不到，
加入者永远卡在大厅，只有房主能玩。

**根因**：提交 `0d5aa0c`（"修复所有场景连接失败问题"）在重构
`_initAsClientInner` 时删掉了 `this.setupHostChannel(conn);` 这一行，
只保留了 `conn.on('open')` / `conn.on('error')`，此后从未补回。
`git log -S "setupHostChannel" -- src/network/lan-peer.ts` 可复现这条线索。

**修复**：在 `conn.on('open')` 回调里重新调用 `this.setupHostChannel(conn)`。
改完 `npm run check` 仍 4/4 通过。

   → 注意 TS 6 必须加 `--ignoreConfig`，否则报 TS5112。

   用 `NODE_PATH=...` 引入；`chromium.launch({ executablePath: 'C:\\Program Files (x86)\\Microsoft\\Edge\\Application\\msedge.exe' })`。
4. **两个 `browser.newContext()`** 隔离 localStorage，才等价于两台机器。
5. 断言：房主点开始后，客户端是否离开大厅（`stillLobby()` 正则匹配
   `加入房间|房间已创建|等待房主开始游戏|玩家 (\d/4)`）。

## 联机架构速记（读代码得来，未改动）
- 信令：自写 PeerJS 兼容服务器。三份实现同协议：
  `electron/peer-server.ts`(Node/ws)、`android/.../PeerServerService.java`(NanoWSD)、
  `capacitor-plugin/`。都监听 9000，占用则退 9001，都提供
  `GET /peerjs/id`、`/peerjs/port`、`/peerjs/key` + WS 升级。
- 数据面：PeerJS DataConnection P2P，`iceServers: []` 关掉 STUN 纯局域网直连。
- 权威模型：**房主权威**。客户端只上行 `play-card` / `pass-card`，房主校验
  （`canPlayCard` + `trickJustCompleted` 宽限期）后 `playCard()` 出新状态再全量广播。
- 传牌：房主收集所有人选牌（自己的走 `lanHostPassRef`，客户端走 `lanPeer.clientPasses`），
  等 `lanPassConfirmedRef` 集齐全部 `isHuman` 玩家后调 `applyCardPass` 一次性推进。
- AI 只在房主端跑（`lanIsHostRef.current` 判断），客户端纯展示。
- 三端取服务器地址优先级：URL hash `#server=host:port` > Android 原生桥 > localStorage > 默认 127.0.0.1:9000。

## 顺带发现（未改，待用户定夺）

# 2026-09-27（三）— 继续深挖，共修复 5 处缺陷

把端到端测试从"能进牌桌"推进到"能真正打完一手牌"后，又暴露出 4 个更深的缺陷。
**根因是同一个设计漏洞：LAN 模式没有贯彻"只有房主改状态"这条不变量。**
改动：`src/App.tsx` +29/-2，`src/network/lan-peer.ts` +3。`npm run check` 4/4。

## Bug 2：客户端根本收不到房主广播（第一轮已修）
`lan-peer.ts` 的 `setupHostChannel()` 无任何调用点 → 客户端永远卡大厅。
提交 `0d5aa0c` 删掉了那行调用。修复：在 `conn.on('open')` 里补回。

## Bug 3：房主无法出牌 —— 点击走错了分支
`App.tsx` 手牌 onClick 在 `mode === 'lan'` 时**无条件**调
`lanPeer.sendToHost('play-card', ...)`，而 `sendToHost()` 开头就是
`if (this._role !== 'client') return false` —— 房主角色直接吞掉。
现象：房主点 38 次牌，PLAYCARD 日志 0 条，手牌不变，游戏死锁在房主回合。
修复：房主分支改调 `handleCardClick(card)`，并在 `handleCardClick` 里补
`if (mode === 'lan' && lanIsHostRef.current) lanPeer.broadcast(newState)`
（房主是权威，自己的出牌也得推给客户端）。

## Bug 4：`waitingForAi` 闩锁 —— 单人模式和联机**都中招**
`waitingForAi` 只在两处被置 true（两个 AI 回合 effect 的 setTimeout 里），
但**只在 `handleCardClick` 里被置 false**。
而 effect 在轮到人类时 `getAiPlayDecision()` 返回 null 直接 return，
于是这个标志一旦置 true 就再没人清 —— 手牌 `disabled={... || waitingForAi}`，
"轮到你了！"也被 `&& !waitingForAi` 挡住 → 死锁。

**单人模式也复现**（用 `git stash` 在原始代码上验证过，不是我改坏的）：
第一次 AI 出牌后横幅永久停在"AI 思考中..."，可点牌 0 张。
只在玩家手握 ♣2 首出时才看不出来。

修复：两个 AI effect 的 setTimeout 里，出完牌立刻 `setWaitingForAi(false)`。
（注意：**不能**在 effect body 里同步 setState，会被
`react-hooks/set-state-in-effect` 判为 error，必须放在 timer 回调里。）

## Bug 5：房主和客户端各自独立洗牌 → 两边拿到的牌完全不同
`Unified Deal Animation Effect`（`gameState.phase === 'dealing'`）在
**两端都会跑**，各自 `Math.random()` 洗牌。房主 4.5s 后广播自己的 `finalState`，
但如果此时客户端本地发牌还没结束，客户端的 `setGameState(finalState)` 会把
房主的结果**覆盖掉** → 两边牌面分叉。
后果：客户端传的 3 张牌在房主手里不存在 → `cardsToPass` 为空 →
`Object.assign(allPassedCards, lanPeer.clientPasses)` 把原本正确的 3 张**覆盖成 0 张**
→ 客户端不交牌却收 3 张 = 16 张牌，下游玩家 10 张，整局错乱。
（3 次连跑 3 次复现；这个"空数组覆盖有效值"的写法本身也很脆。）

修复：发牌 effect 开头加 `if (mode === 'lan' && !lanIsHostRef.current) return;`
—— 客户端不洗牌、不发牌，只渲染房主广播的结果。

## 复现/验证要点（下次直接用）
- 手牌是**扇形叠放**（负 margin），Playwright 点元素中心会打到**下一张**。
  必须 `click({ position: { x: 8, y: 24 } })` 点左侧露出的部分。
- 选牌选择器**不能**用 `[aria-label*="点击选择传递"]` —— 它会先匹配到
  容器 `<div role="list" aria-label="你的手牌（点击选择传递）">`，
  导致 3 次点击只选中 1 张、「确认」一直是 disabled。
  必须用 `[role="button"][aria-label*="点击选择传递"]`。
- 出牌阶段的手牌容器 aria-label 是**精确**的 `你的手牌`，
  传牌阶段是 `你的手牌（点击选择传递）`，可以据此判断阶段。
- 判断"是否轮到我"：页面上是否出现文本 `轮到你了！`。
- **决定性断言**：玩家自己的手牌数量只有在收到房主广播后才会变。
  所以「手牌数减少」= 上行被接受 + 下行广播收到，一次证明双向通了。
- 传牌阶段的「确认」按钮在 480x800 / 1280x800 / 390x844 / 844x390
  四种尺寸下都实测可点（`document.elementFromPoint` 命中 BUTTON 本身），
  之前那次"被手牌挡住"是选择器错误的假象。

## 仍然没动的三处（待用户定夺）
1. `handleGuestMessage` 里 `data.type === 'join'` 是死代码（JOIN 走信令 WS）。
2. `localStorage` 的 `heart-lan-server-port` 跨端传端口，同源多标签页会互相干扰。
3. `setupHostChannel` 的 `conn.on('close')` → `connection-error` → 文案"连接错误，请重试"偏误导。
4. 另外：`playCard()` 和房主的 `handleCardPlay` **都不校验出牌顺序**，
   恶意客户端可以替别人出牌 / 抢出。局域网内可接受，但值得知道。

# 2026-09-27（六）— 手机↔手机的联机链路（只查，未改）

## 结论：没有服务发现，靠人工抄 IP
两台手机各自跑一个**内嵌 PeerJS 信令服务器**（`PeerServerService`，前台服务，
NanoWSD，9000 → 占用则 9001），但**只有房主那台的被用到**。
- **A（房主）**：`initAsHost` → `resolveServerConfig()` 轮询原生桥拿自己的 WiFi IP + 端口
  → 用 `ws://<自己的IP>:9000` 连自己的服务；房号就是 PeerJS 的 peer ID。
  大厅显示 `连接地址：<A的IP>:<端口>`（端口那处我刚在 `87ce2f5` 修成真实值）。
- **B（加入者）**：**必须人工把 A 屏幕上的 IP 和房号填进「加入别人房间」表单**。
  代码里搜遍 `nsd|mdns|zeroconf|multicast|discover|qrcode` 都没有实现 ——
  没有自动发现、没有扫码、没有局域网扫描。
- 连上 A 的信令后交换 SDP/ICE，随后两台手机**直接 P2P**（`iceServers: []`，无 STUN，纯局域网）。
  权威状态始终在 A。

Android 侧放行条件都齐：`usesCleartextTraffic="true"` +
`network_security_config.xml` 的 `cleartextTrafficPermitted` +
`capacitor.config.ts` 的 `androidScheme: 'http'` + `MIXED_CONTENT_ALWAYS_ALLOW`。

## 查到的问题（Android 专有，浏览器 E2E 覆盖不到）
1. **加入者的端口会被自己的端口无条件覆盖** —— `lan-peer.ts` 的 Android 分支：
   ```js
   if (nativePort > 0) {
     this.serverConfigInternal = { ...this.serverConfigInternal, port: nativePort };
   }
   ```
   `nativePort` 是 **B 自己** 的服务器端口，却覆盖了用户为 **A** 填的端口。
   两台都绑 9000 时看不出来；一旦 A 因 9000 被占回退到 9001，B 仍会连 A 的 9000 → 必失败，
   而界面上那个端口输入框是假的（填了也没用）。
   这和我上一轮删掉的 `heart-lan-server-port` 是**同一种"无条件覆盖"写法**，
   当时只查了浏览器路径所以漏掉了。
2. **每次启动都拉起前台服务**：`MainActivity.onCreate` 无条件 `startPeerServer()`，
   所以只玩单机也会常驻一条「红心大战服务器」通知。
3. **`capacitor-plugin/` 是死代码**：`package.json` / `capacitor.config.ts` 都没引用它，
   里面的 `PeerServerPlugin.java` 与 Android 工程里那个重复。
4. **IP 注入晚于页面加载时的降级风险**：`MainActivity` 在 WebView 进度 100 时注入
   `window.__serverPort`；若此时服务还没 `saveServerPort()`，注入的是 `-1`。
   `resolveServerConfig()` 里是 `window.__serverPort ?? bridge.getServerPort()` ——
   `-1` 不是 null/undefined，`??` 不会回退到桥，轮询 8 次也没用，
   于是 `initAsHost` 用默认 `localhost:9000`，大厅就会显示「localhost」→ B 没法用。

## ① 端口被本机覆盖的 bug（已修 + 已验证）
`_initAsClientInner` 的 Android 分支里 `if (nativePort > 0)` 无条件用**本机**端口
覆盖用户为**房主**填的端口。新增 `_portExplicit` 标志（`setServerConfig()` 里置位），
改成 `if (nativePort > 0 && !this._portExplicit)`。

### 验证手段（很值得复用）：用 initScript 伪造 Android 环境
`context.addInitScript()` 在页面脚本之前注入
`window.__localIp / window.__serverPort / window.AndroidBridge`，
`detectAndroid()` 就会认定这是 Capacitor WebView。然后：
- 手机 A（host）：伪造 `__serverPort=9001`，信令服务器**真的**只跑在 9001
- 手机 B（guest）：伪造 `__serverPort=9000`，加入表单里填 **9001**
- 判定：B 能否连上（9000 上没有任何服务，所以填的端口被覆盖就必失败）

**A/B 结果**：修复前 `Final Android server config: port 9000` + 加入失败；
修复后 `port 9001` + 加入成功。脚本存于 `/d/dev-tools/tests/android-join.js`。

# 2026-09-27（八）— 还原 pre-API-26 启动图标

   `android:pathData/fillColor/strokeColor/strokeWidth/fillType`，

   `android:startX/startY/endX/endY` → `x1/y1/x2/y2` + `gradientUnits="userSpaceOnUse"`）。
